# 模型与转录的局限

本文解释当前 piano transcription 系统**做不到什么、为什么做不到**，尤其是：

- 回放听起来比乐谱“丰富”；
- 快速内容、琶音、短倚音、三连音容易缺音或记错；
- 播放时谱面高亮仍可能和声音不同步。

结论先说：**这不是单一 bug，而是 32 ms 帧率、事件解码、乐谱量化和
原始音频/谱面两条时间轴共同造成的系统性限制。**

## 1. 回放比乐谱“音更多”

回放和乐谱走的是两条不同的数据路径：

```text
回放：NoteEvent 列表 + pedal CC64 → playback.mid → FluidSynth
乐谱：NoteEvent → 去重/量化/和弦/时值拆分 → MusicXML → PDF
```

因此“听起来音更多”可能来自：

1. **踏板延音**：回放有 CC64 踏板，钢琴共鸣和延音让声音更丰富；谱面不会把
   每个泛音都记成音符；
2. **同音去重**：同一音高、同一量化起点的重复事件在谱面只保留一个；
3. **和弦化**：同时起音的音会合并成和弦，谱面音符数看起来变少；
4. **量化**：接近的起音被吸到同一节拍网格；
5. **时值拆分/连音**：跨小节或超长音会拆成多个 note 元素，数量可能反而变多；
6. **页面限制**：app 最多渲染 20 页，长曲目后面的谱面不可见，但音频仍完整。

## 2. 快速内容为什么容易缺

模型和标签的时间分辨率是 32 ms/帧（31.25 fps）。这带来几个硬限制：

- 两个音如果落在同一帧、同一键上，模型很难区分；
- onset 解码使用峰间距（`peak_distance` 默认 5 帧，约 160 ms）和阈值，
  快速重复音、颤音、快速同音重复可能被抑制；
- 快速跑动的相邻音可能被合并成一个更长的音，或只保留其中一部分；
- 极短的音可能低于 onset 阈值，或在 offset 端无法稳定配对。

## 3. 琶音、短倚音、三连音

### 琶音

琶音是一组“几乎同时但略有先后”的音。当前模型可以检测到这些音，但乐谱层会：

- 把量化到同一 16 分音符位置的音合并成和弦；
- 丢失音与音之间几十毫秒的先后关系；
- 快速琶音可能被记成柱式和弦，听感与谱面不一致。

### 短倚音 / 装饰音

短倚音通常只有几十毫秒，容易：

- 被 onset 阈值或峰间距过滤；
- 与相邻主音合并；
- 在量化时被吸到主音位置；
- 当前记谱没有专门的倚音/装饰音识别与符号。

### 三连音 / 连音

乐谱量化网格是 **1/4 拍（16 分音符）**，`STANDARD_QL` 只包含
4、3、2、1.5、1、0.75、0.5、0.25 拍等标准时值。当前**不生成 tuplets（连音）**：

- 三连音、五连音、七连音会被近似成普通 8/16 分音符；
- 速度快的三连音可能被合并或错位；
- 附点节奏与 swing 也会被拉直。

## 4. 踏板与时值

- 模型学的是 key-off 的 offset，踏板状态另有一个 `pedal` 头；
- 回放使用踏板区间 CC64，但谱面的踏板线只是装饰性表示，不等于精确踏板演奏；
- app 的 `smooth_pedal_events()` 会合并 ≤ 0.90 s 的间隔并延长 0.12 s 尾巴，
  减少硬切断，但也可能造成“过度连踏板”；阈值需要按听感调整；
- SOTA 的 note-off 更接近声学延音，而我们的 GT 是 key-off，note F1 口径不同。

## 5. 为什么播放时音画会不同步

当前 app 有两个时间轴：

| 时间轴 | 用途 |
|---|---|
| 原始音频时间 | `preview.wav`、`playback.mid`、`NoteEvent.start/end` |
| 量化谱面时间 | MusicXML、PDF、小节位置 |

高亮对齐的做法是：

1. 用 verovio timemap 取得谱面实际时长；
2. 用每个量化起音的「音频时间 → 四分音符位置」锚点做局部插值，而不是整首按比例缩放；
3. 每 0.04 s 查询一次当前谱面元素；
4. 用音频 `currentTime` 驱动高亮和翻页。

剩余误差来自：

- 谱面量化/速度估计与原始演奏不是严格线性关系（rubato、渐快渐慢）；
- 锚点只能修正有音符的位置，长休止或漏检处仍会退回局部/全局插值；
- 0.04 s 采样间隔本身有最多约 40 ms 的边界延迟；
- 浏览器音频解码/播放延迟、页面切换和渲染开销；
- 小节高亮依赖 verovio 当前 measure 元素，快速段落可能刚好落在切换边界；
- 长曲目页数多，越往后累计漂移越明显。

因此我们看到的现象是：**默认情况下大体对齐，但快速段落和长曲目末端仍可能差几十毫秒。**

### 5.1 测量真实高亮延迟

app 内置了浏览器端埋点。打开：

```text
http://127.0.0.1:8000/?sync=1&job=<job_id>
```

播放后，每次高亮元素变化都会记录：

- `audio_t`：浏览器音频 `currentTime`；
- `score_t`：时间轴采样本应切换的时间；
- `lag_ms`：两者差值，即 UI 高亮实现延迟；
- 页码、小节和采样序号。

播放一段时间后，可点击左下角「导出同步报告」，或在浏览器控制台执行：

```javascript
piano2SyncStats()
```

在 20 秒钢琴片段、1 页、70 个采样上实测：

| 指标 | 数值 |
|---|---:|
| p50 | 6.7 ms |
| p90 | 13.3 ms |
| p95 | 15.4 ms |
| max | 17.5 ms |

这说明高亮更新本身不是主要瓶颈；更大的误差来自「音频时间 → 谱面时间」的映射和量化，而不是浏览器渲染。该测量是**相对时间轴采样的 UI 延迟**，不是完整链路的音画真值误差。

## 6. 和 SOTA 的差距

在 3 段 validation 的 head-to-head 中：

| 指标 | 当前路线 | ByteDance SOTA |
|---|---:|---:|
| onset F1 @50 ms | 0.929 | 0.983 |
| onset F1 @10 ms | 0.513 | 0.901 |
| note-with-offset F1 | 0.362 | 0.444 |

当前 hybrid_reg2 在 test split 上把 10 ms onset 提到 0.626、note-with-offset 提到 0.379，
但仍明显低于 SOTA 的 0.90/0.444。差距主要来自输入时间分辨率、直接高分辨率回归头和
训练规模，而不是单纯“再调一下解码阈值”。

> 表中 validation head-to-head 是 offset 窗口修复前的对比记录；修复后的完整
> test split 指标见 [`09_app_changelog.md`](09_app_changelog.md) 和 README。SOTA
> 三方对照尚未在修复后重跑，因此不要把这张表当成最新排名。

## 7. 可以怎么缓解

| 方向 | 说明 |
|---|---|
| 更细的 CQT hop | 16 ms / 8 ms 能从输入层提高时间分辨率，代价是数据和训练成本 |
| 局部 refiner | 在候选 onset 附近裁 CQT，用单独网络回归精确时间 |
| 相位分类头 | 把帧内相位变成离散类别，避免三角回归峰值变平 |
| 连音/装饰音识别 | 在解码后增加 tuplets / grace note 规则或专门分类器 |
| 局部时间映射 | 用拍点/小节边界做分段映射，而不是全曲线性缩放 |
| 生成演奏谱 | 保留原始时间轴，不强行压到 16 分音符网格 |

## 8. 怎么判断是“模型漏音”还是“记谱丢了”

1. 看 app 结果里的原始 `n_events` 与音频试听：回放里有、谱面没有 → 记谱/页面问题；
2. 用 `playback.mid` 和 `score.mid` 对比：前者是原始事件，后者是谱面时间轴；
3. 导出 piano-roll 或原始事件表，核对具体时间；
4. 检查是否超过 20 页、是否被量化/和弦/去重。

如果某一段具体音频在回放里也听不到，那才是模型漏检；如果回放有而谱面没有，
优先检查记谱量化和页面限制。
