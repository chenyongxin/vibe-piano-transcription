# 07 路线图：M3 训练与 M4 应用

## 1. M3：全量训练

> 状态：**已完成（2026-11-05，RTX 4060 上跑 20 轮 = 71,160 步）**。
> 实际结果：验证 F1 最佳 0.7656；三首开发曲目 onset F1 0.970 / 0.962 / 0.820；
> 留出集 onset F1 0.870、精确率 0.860（**预注册判据达标**）；
> 时值仍不达标（note-with-offset 0.19 / 0.38 / 0.28，留出集 0.063），
> 转入 M3.5（offset 头 / 1 帧 onset / 数据增强）。下方保留原计划作为记录。

### 1.1 目标与预注册判据

在训练开始前先把判据写死，避免事后挑数字（预注册，pre-registration）：

| 指标 | 判据 | 依据 |
|---|---|---|
| onset-only F1（留出集） | ≥ 0.85 | 解码器在留出集已达 0.821，模型训练后应进一步提升 |
| 精确率（留出集） | ≥ 0.85 | M0.5 的硬约束，当前 0.835，差 0.015 |
| note-with-offset F1（三首开发曲目） | ≥ 0.60 | 旧模型约 0.18（因时值标签口径），M3 应显著改善 |
| 黑音符占比（nezha2） | ≤ 0.72 | 记谱层已达标，训练不应让它变差 |

如果训练后 onset F1 没有 ≥ 0.85，**不调参硬凑**；先按「训练量 / 标签 / 特征 / 解码」四层排查，
把原因写进实验登记表。

### 1.5 M3.5：时值修复（下一步）

**诊断依据**（2026-11-05，用全量训练后的 best.pt）：

| 曲目 | onset F1 | note F1 | 换成 GT 结束时间后的 note F1 | 预测/GT 按键时长比 |
|---|---|---|---|---|
| Haydn | 0.970 | 0.186 | **0.969** | 3.23 |
| Beethoven | 0.820 | 0.279 | **0.816** | 2.95 |

结论：note F1 的损失几乎全部来自**结束时间**；偏差由两部分叠加——
（a）训练 frame 含踏板、评测用 key-release 口径不一致（主因）；
（b）帧释放检测本身偏晚（即使按含踏板口径比，仍偏长 25%–50%）。

**实验计划（2026-11-05 晚通宵队列，按顺序执行）**：

| 顺序 | 实验 | 内容 | 数据 | 成本 | 判据 |
|---|---|---|---|---|---|
| 1 | **D2** | frame 改为 `frame_key`（不含踏板），5 头模型训练 20 轮 | v3a | 1.6 小时 | note F1 明显上升（Haydn ≥ 0.45、Beethoven ≥ 0.40） |
| 2 | **A** | 增加 **offset 头**（第 6 头，offset 损失 1.0），解码时用 offset 峰定结束 | v3b | 1.6 小时 | 在 D2 基础上继续提升；与 GT 时值口径一致 |
| 3 | **B** | 1 帧 onset 重训 20 轮（已有 onset1 通道） | v2 | 1.6 小时 | onset F1 是否优于 2 帧 |
| 4 | **C** | 数据增强：频率遮蔽 2 条 + 时间遮蔽 2 条 | v2 | 1.6 小时 | 验证 F1 / 泛化是否提升 |

**实现要点**：

- 数据 v3a：只替换 frame 通道（frame_key），CQT/pedal 硬链接，45 秒构建完成；
- 数据 v3b：在 v3a 上增加 offset 通道（note-off 帧起 2 帧），offset 正样本率约 0.69%；
- 模型：增加 `fc_offset` 第 6 头（总参数 1149.6 万，+4.5 万），训练用 `--offset-loss 1.0`；
- 解码：`DecodeConfig.use_offset_end=True` 时，从起点后找第一个 offset 峰作为结束时间，
  找不到退回原来由 frame 推断的结束时间；
- 评测：A 实验的 `evaluate.py` / `evaluate_holdout.py` 加 `--offset-end`。

**决策闸门**：

- D2 后 note F1 达到 0.5 以上 → 口径是主因，继续完善 offset 通道与解码；
- D2 后仍低于 0.4 → 重点看 A（offset 头）是否有额外提升；
- 留出集的 onset 精确率不要回退（当前 0.860，余量只有 0.01）。

### 1.6 首轮实验结果（2026-11-06，四组各 20 轮）

| 实验 | 验证 F1 | 开发集 onset F1（H/M/B） | 留出集 onset F1（P/R） | 留出集 note F1 |
|---|---|---|---|---|
| baseline（EXP-002） | 0.7656 | 0.970 / 0.962 / 0.820 | 0.870（0.860 / 0.880） | 0.063 |
| D2（frame_key） | 0.763 | 0.966 / 0.962 / 0.819 | 0.866（0.867 / 0.865） | 0.170 |
| **A（offset 头）** | **0.779** | 0.963 / 0.961 / 0.808 | 0.876（0.884 / 0.868） | **0.268** |
| B（1 帧 onset） | 0.809* | 0.974 / 0.968 / 0.824 | 0.870（**0.901** / 0.841） | 0.053 |
| C（数据增强） | 0.766 | 0.968 / 0.964 / 0.798 | **0.878**（0.895 / 0.862） | 0.060 |

\* B 的验证 F1 是 onset1（1 帧标签）口径，标签更窄，数值不能与 baseline 的 2 帧口径直接比较。

**结论**：

1. **A（offset 头）是时值方向的最佳方案**：留出集 note F1 从 0.063 提到 **0.268（约 4.2 倍）**，
   开发集 Haydn 0.186→0.281、Mozart 0.380→0.408；但 **Beethoven 0.279→0.154 明显回退**，
   而且 onset 也略降（0.820→0.808），需要单独排查。
2. **B（1 帧 onset）显著提高精确率**：留出集 precision 0.860→**0.901**，F1 持平；
   开发集三首 onset F1 都略高于 2 帧。代价是召回率下降（0.880→0.841）。
   进一步分析（贪心匹配 GT）：2 帧模型的起点中位偏差 +14.7/+12.9 ms，1 帧模型约 -0.5/-1.1 ms，
   所以 1 帧的收益主要是去偏，而不是新增信息；第二帧在标签构造上被强制为正，
   对短音还会与 frame 标签冲突（onset 后 32 ms 仍有发声的仅 66%–81%）。
3. **C（数据增强）拿到最高留出集 onset F1 0.8784 / precision 0.8954**，
   但开发集 Beethoven onset 掉到 0.798，note 指标不变。
4. **D2（只改 frame 口径）不够**：留出集 note 从 0.063 升到 0.170，
   但开发集 note 反而下降，说明单靠标签口径修不好时值。
5. 四组验证 F1 都不低于 baseline（A 0.779 最高），说明 offset 监督没有破坏整体学习。

**下一步（待讨论确认）**：

| 优先 | 内容 | 成本 | 目的 |
|---|---|---|---|
| 1 | 对 A 模型做解码端网格搜索（`offset_threshold` / `offset_min_frames` / `offset_max_frames`） | 约 15 分钟，无需训练 | 看 Beethoven note F1 能否回升 |
| 2 | 组合实验：data_v3b + **onset1** 标签 + offset 损失 | 约 1.6 小时 | 同时拿 onset 精确率与时值收益 |
| 3 | 分析 Beethoven 的 offset 错误模式（漏检/多检/搜索窗越界） | 约 30 分钟 | 决定改标签、改解码还是加训练 |
| 4 | 应用侧启用 offset 解码，真实曲目人工听感验证 | 约 1 小时 | 验证谱面可用性 |

详细人可读报告见 `training/2026-11-05_m3_full_71k.md` 与 `training/2026-11-06_m3_5_nightly.md`。

## 2. M4：浏览器应用

### 2.1 目标

用户上传钢琴录音 → 等几十秒 → 网页上看乐谱、播放、下载 MusicXML / MIDI / PDF。

### 2.2 技术选型（待确认）

| 部分 | 方案 | 理由 |
|---|---|---|
| 后端 | FastAPI | Python 生态一致，异步够用 |
| 推理 | 与 `scripts/transcribe.py` 同一套代码 | 不重复实现 |
| 渲染 | verovio + rsvg（已有） | 成熟排版引擎，不自己造 |
| 前端 | 单页（HTML + 少量 JS） | 需求简单，不上框架 |
| 部署 | 本机 Docker 或单进程 | 个人使用，先不云部署 |

### 2.3 里程碑

1. 本地能跑通「上传 → 出谱 → 下载」；
2. 加上播放（用 MusicXML 或 MIDI 回放）；
3. 再加参数面板（阈值、踏板开关）；
4. 最后考虑用户体验（进度条、错误提示、批量处理）。

## 3. 风险清单

| 风险 | 影响 | 对策 |
|---|---|---|
| 4090 上训练不稳定（NaN、显存不足） | 训练中断 | 先用 pilot 配置在 4090 上跑 100 步验证；保留 4060 作为回退 |
| 留出集精确率仍差 0.015 | 达不到硬约束 | 不靠调解码参数，改训练/特征；若仍不行，如实报告并说明原因 |
| 数据 v2 与旧数据路径混淆 | 训练用错数据 | 用 manifest 指纹核对；constants 环境变量显式指定 |
| 应用端推理慢 | 体验差 | 滑窗推理 + 概率缓存；必要时限制音频长度 |
| 项目烂尾 | — | 每个里程碑都有可交付物与判据；M3 结束先出一版能用的乐谱 |

## 4. 决策闸门

| 闸门 | 通过条件 | 不通过怎么办 |
|---|---|---|
| M3 训练完成 | 预注册判据 4 项中至少 3 项达标 | 分析原因，下一轮只改一个变量 |
| M3 → M4 | 乐谱在 3 首真实曲目上人工看「能读」 | 先修记谱层，不上应用 |
| M4 上线 | 本机完整流程可重复跑通 | 继续打磨，不上线 |

| 阶段 | 预计 | 说明 |

| M3 | 1–2 天 | 训练 1–2 小时 + 实验与报告 |
| M4 | 3–5 天 | 后端 1 天、前端 1–2 天、联调 1 天 |
